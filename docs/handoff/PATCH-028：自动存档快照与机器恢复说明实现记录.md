# Patch 028：自动存档快照与机器恢复说明实现记录

## 来源与范围

第二十四次 Patch 027 合并后黑盒验收确认 D52 自动保存缺陷已经消失，同时记录一项机器可理解性观察：`autosave_end_day` 文件是包含 `slot / settled_day / state / logs / resume_stage` 的日期推进前快照封装，不能直接作为普通主存档交给 `play` 或 `report`；旧入口只返回 `SaveDataError`，机器必须靠失败和文件结构猜测正确用途。

本 Patch 只公开既有持久化合同，不改变自动保存时机、事务回滚、主存档内容、存档版本、报告格式、游戏机制或平衡数值。

## 正式接口

- 完整观察的 `protocol_contract.persistence_files` 区分：
  - `game_state`：可由 `play` / `report` 接受、代表当前已提交状态的主存档；
  - `end_day_autosave_snapshot`：位于当日清理后、日期推进前的只读事务快照，不覆盖也不替代主存档。
- `status.persistence` 紧凑返回主存档是否配置、最近自动保存是否存在、自动保存不是主存档，以及正式查看请求形状。
- `play` 新增查询包络 `{"type":"autosave"}`：
  - 尚未成功日结时返回 `available=false`；
  - 有磁盘槽时严格读取顶层字段、嵌套完整状态和每条结构化日志；
  - 返回 `settled_day`、`resume_stage`、锁定的完整 `state`、日结 `logs` 与文件角色合同；
  - 查询只读，不修改状态、存档、回放或序列。
- 直接把合法自动存档快照路径用于 `play` 或 `report` 时，返回稳定错误 `AUTOSAVE_SNAPSHOT_NOT_PRIMARY_SAVE`，明确：
  - 当前文件角色为 `autosave_end_day`；
  - 它不被接受为主存档；
  - 应打开同一持久化集合中的主存档；
  - 打开主存档后使用 `{"type":"autosave"}` 查看；
  - 不得自行提取嵌套 `state` 作为主存档。

## 兼容与严格性

- 不改变 v17 `GameState`，不新增存档迁移。
- 不改变既有自动存档 JSON 形状；Patch 011 至 Patch 027 产生的合法快照可直接通过新包络查看。
- 自动存档损坏不会阻止完好的主存档加载；请求查看损坏快照时严格拒绝，不用忽略字段或降级解析掩盖问题。
- 本轮不把推进前快照实现成新的恢复点。`resume_stage` 的执行、日期推进幂等、主/副槽选择和崩溃恢复优先级没有完整封存合同，继续登记在 `docs/PENDING.md`。

## 测试

- 新局首次日结前自动存档显示不可用。
- 成功日结后，当前会话与重启会话均能通过正式包络读取 D1 锁定快照、日志及 `resume_stage=advance_day`。
- `status` 与完整协议合同在提交失败前即可发现文件角色和查看方法。
- 同一自动存档路径交给 `play` 与 `report` 均返回相同稳定错误、主存档候选和禁止提取说明。
- 即使显式请求覆盖新建，也不能把合法自动存档快照覆盖成主存档；拒绝后原文件字节不变。
- 自动存档增加未知字段时，主存档仍可正常加载，但只读查看严格拒绝。
- 使用第二十四次黑盒交付的真实旧快照复验：正式包络成功读取 D55 `final_settlement` 锁定快照；直接路径稳定返回专用错误；主存档和自动存档 SHA-256 均保持不变。
- 全量 `unittest`：454 项通过；9 份 JSON 配置校验、`compileall` 与 `git diff --check` 通过。
