# Patch 026：资源耗尽结果与序列语义实现记录

## 来源与裁决

本轮依据 Patch 025 合并后的纯黑盒验收，处理两项低风险机器可理解性问题：资源点在日结中耗尽后，紧凑返回未直接说明岗位已经释放；回放条目的 `replay_sequence` 与游戏结果的 `state_sequence` 缺少并列合同说明。

验收报告同时质疑旧城事件 ID 与选项 ID 的映射。复核确认现有 `old_city_view` 在活动事件存在时已经返回 `pending_event_id`、`available_option_ids` 及逐项 `option_previews`，足以确定事件、合法选项与结果预览，因此该项属于验收误判，本轮不修改旧城实现。

本轮不调整地图、资源储量、产能、建筑、科技、炉律、事件、社会路线、天气、终霜门槛或其他平衡值；不新增推荐行动、自动策略、存档字段、迁移、图形界面、D56 或 Patch 027。

## 资源点耗尽的同日结果

- 地表资源点在正式生产阶段归零时，继续沿用原有耗尽、清除生产余数和自动释放岗位逻辑。
- 同一成功日结的 `warnings` 新增 `buildings.resource_points_depleted`，评估阶段固定为 `settlement_result`。
- 结果按资源点 ID 稳定排序，列出资源点 ID、资源类型、分别释放的工人/工程师、两类岗位总数，并明确 `assignments_released_automatically=true`、`unassign_required=false`。
- 同一事实进入正式日结返回、结构化日志与回放；失败或回滚日结不会提交该结果。
- 不建议释放人员接下来应被派往何处，也不改变收集、储量、产出或耗尽规则。

## 两种序列的正式语义

机器观察的 `protocol_contract.sequence_semantics` 并列公开：

- `replay_sequence`：只属于当前打开的 `GameSession`，不写入存档；为实际进入回放的命令尝试编号，包含被拒绝的有效命令请求，无法形成回放条目的格式错误可为 `null`；重开会话后从头编号，不能用于乐观并发。
- `state_sequence`：属于持久化游戏状态并写入存档；只在状态成功提交时递增，拒绝命令不递增；重开会话后保留，由请求字段 `expected_state_sequence` 执行乐观并发校验。

该合同只解释既有行为，不修改回放格式、命令结果形状或存档版本。
