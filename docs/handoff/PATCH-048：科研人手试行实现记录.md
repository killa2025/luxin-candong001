# Patch 048：科研人手试行实现记录

## 来源与范围

用户在讨论科研/医疗争夺人手后，明确同意先试“10 人维持原速、少人按比例慢研”，不定成最终数值。本轮只改变新局科研人手与速度关系及所需保存/查询接口。旧资料第三批 4.3 的“一名工程师即可完整基础速度”不是 Bug；其作为旧局规则保留，封存源文件不回改。

基于 main `681fd09c87a3194eaa0ec20661a364a2d21e0f2c`，工作分支 `patch/048`。不直接推送 main；独立提交、Draft PR，审核前不合并。Patch 047（含 PR #52 加热发现性）已通过定向黑盒，更新 INDEX/PENDING 的陈旧状态。

## 试行规则（USER_OVERRIDE / TEST_NUMERIC）

- 每座研究所 10 名正式工程师达到现有完整基础速度 4 研究点/日；5 人 2 点、1 人 0.4 点、0 人不推进。
- 仍最多两座研究所、每所 10 岗、唯一研究队列；不新增建筑、命令或科技。
- 每座基础贡献 `b_i = progress_units_per_day * engineers_i / staffing_full_engineers`。
- 对实际加班的那座按既有倍率 1.5 计算 `c_i`，其他座 `c_i=b_i`。
- **加班后**重新比较贡献：`max(c_i) + 0.5 * min(c_i)`；只有一座时只用其贡献，无可运行正式工程师则 0。第二座的 0.5 取自既有第二所 1.5 倍总速率减去 1。
- 不使用建造顺序决定主副研究所，不把一座加班变成全队列加速。两所满员正常 6 点/日，只有一所加班为 8 点/日；单所满员加班仍 6 点/日。
- 在既有 `ADVANCE_AND_COMMIT_RESEARCH` 阶段读取当时可运行研究所的合法工程师派员；此前医疗、死亡等按原顺序执行，不复用白天预测人数，不改变日结阶段。
- 使用精确有理数计算、十分点持久化，不用浮点；没有工作时保留当前项目已有进度。完成或取消时清空全部小数与溢出，不转入下一项科技，不退款。
- 工程学徒额外贡献仍为 PENDING，不增加或猜测系数；不改变其其他既有规则。

## 配置、存档与接口

- `data/technologies.json.research.staffing_full_engineers = 10` 是本轮唯一新增配置项，仍标 TEST_NUMERIC。既有科技成本、研究工作量、第二所倍率、加班倍率不改。
- 存档 v19：`TechState.research_profile_id` 与 `research_remainder_tenths` 均必需。余数必须为非布尔整数 0～9，无项目时为 0。
- 新正式开局为 `staffing_patch048`，寒冷和评分档仍为 `patch045`，不捆绑改动其他平衡系统。
- v18 → v19 只补 `legacy_fixed` 和零余数，原研究整数进度、已支付成本、活动项目、寒冷/评分档、每日历史和报告原样保留。旧局继续原固定研究速度与整队列加班语义。
- 拒绝旧版本伪带新字段、未知科研档、legacy 带非零余数、无项目带余数等。旧迁移测试只补移除当时不存在的 v19 字段，不放宽生产读档校验。旧科技测试明确使用 legacy 档继续覆盖原规则；新规则另测。
- 原整数 `research_progress_units` 单位不变；总进度为 `10 * research_progress_units + research_remainder_tenths` 个十分点。完成日志另记被丢弃的超额十分点，余数最终为零。
- `observe().research_view`、CLI state、`status().research.speed_contract`、`rules(technologies).interface_text.research_speed` 同源公开科研档、当前贡献、公式、加班范围、精度与研究阶段。
- 观察中的速度是当前状态能力，明确不是未来伤亡/人员变化后的日结保证。开始研究预览将名义 `research_days` 标为工作量而非当前人手下的完成日期；取消预览包含将丢失的精确十分点。
- 新增玩家 `text_id`：无。只公开机器事实，不写推荐行动、策略或新剧情。

本轮结果：571 项 unittest 全部通过（含新增 13 项、两条 D1～D55 正式命令路径）；9 份 JSON 配置校验通过；compileall 与 diff check 通过。另只读加载第四十六次真实 v18 终局主存档，逐项比对 `final_result`、`final_frost` 与原文件相同，科研档为 `legacy_fixed`。

首轮审核发现：若外部把基础研究点改成不能由十分点精确表示的数值，单文件形状校验仍会放行，直到目标研究所提交加班后才可能在查询中失败。修复后，完整配置树与 `GameSession` 组装都会穷举两座研究所 0～10 人及无加班/任一目标加班的全部合法组合；任何结果不能精确保存为十分点的配置在开局前即被拒绝。另专项验证该人手组合下加班命令保存失败会完整回滚，正式配置成功提交后查询、保存与复载一致，不会留下半提交状态。

另有两条完整正式 D1～D55 记录回归：只调用 GameSession 命令，不注入人口、资源、研究完成或终局事实，不跳日，不产生 D56。固定指令位于 `tests/fixtures/patch048_switch7-v1.json` 与 `patch048_switch5-v1.json`。确认令牌每次由当次预览生成，不复用历史令牌。

## 可行性探针：不是盲玩、不是难度定论

施工侧以第四十六次 seed46047 的历史命令作为固定建设计划素材，明确替换科研优先序与工程师安排，使用当前新局从 D1 运行，不编辑 GameState、不赠送资源。旧报告和旧证据只读。固定建设计划可能与研究延迟不匹配；记录所有拒绝及重试，不能把脚本停止说成游戏不可继续。

| 探针 | 安排 | 实测结果 | 能支持什么 |
| --- | --- | --- | --- |
| high-v2 | 每所研究上限 10；医疗按预定日程留人 | D55 普通胜利，148 存活/0 死亡，食物总量 0 | 至少存在完整合法通关路径，不代表普遍容易或无风险 |
| switch7-v1 | D1～18 上限 10，D19 起每所上限 7 | D55 22 分普通胜利，148/0，食物总量 0 | 不必全程每所 10 人，也能通关 |
| switch5-v1 | D1～18 上限 10，D19 起每所上限 5 | D55 24 分高胜，148/0，食物总量 405 | 候选档仍存在高胜路径，**不认定高难度目标已经达到** |
| medium-v1 / low-v1 | 从 D1 每所上限 7 / 5，却沿用旧建设时间 | D12 首具遗体重大事件未在固定脚本中预设处理，因此停止；均 91 存活/1 死亡，未终局 | 尚未验证从开局少人研究的完整可挽回路径；不是死局证明 |

high-v1 因测试脚本误读不存在的 `ending_report` 属性在首日日结后停止。其存档保留；修正脚本后另开 high-v2，没有将中断探针冒充唯一盲玩。探针本身是可重复的施工实验，不适用“唯一一次纯盲玩”的统计口径。

原始探针脚本及全部成功/拒绝响应、主存档、自动存档、每日指标与摘要保存在施工工作区 `outputs/patch048_feasibility.py` 与 `outputs/patch048-feasibility/`。两个完成路径已抽取其成功命令作为仓库自包含回归，抽取时只替换确认令牌流程，保留实际操作顺序；不包含自动策略代码。

三条完整路径并非随机抽样，不能计算胜率，不能证明“普通图须玩几次才赢”。三者的研究完成数量、建造时点和资源消耗也不同，不能仅凭最终分数判断人手减少一定提高收益。仍需独立盲玩与针对工程师受损的经营验证。
